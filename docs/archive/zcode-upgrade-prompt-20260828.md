# 给 ZCode 的改造 Prompt（评审视角升级版）

## 第一部分：背景与改造目标（先发）

### 项目背景

现有系统是“安全需求与设计基线生成工具”的 MVP，已实现：8 步项目信息向导、规则引擎（38 条知识库模板）、SBOM 生成与 OSV 漏洞匹配、4 份 Word 文档、Excel 需求跟踪表。技术栈：FastAPI + SQLAlchemy + SQLite / React + TS + AntD。
**现在要做一次重要的定位升级**：从“帮项目经理写文档的工具”升级为**“嵌入行内项目评审流程的安全准入管理平台（需求+设计阶段）”**，服务对象从项目经理扩展到安全中心评审员、评审委员会、内部审计。核心新增三类能力：

1. **监管合规基线映射**——每条产出可追溯到监管条款
2. **数据分级标准对齐 JR/T 0197-2020**（5 级体系替换现有 4 级）
3. **评审流程与门禁留痕**——评审意见、签字、版本、放行结论

### 改造总原则

- **存量兼容**：已有项目数据可平滑迁移（老 4 级 → 新 5 级的映射规则见下文）
- **模板与知识库均为数据文件**，修改不涉及代码变更
- **门禁必须硬校验**，不满足条件接口返回明确阻断原因，不允许“提示后仍可提交”
- 所有新增界面文案、文档内容均为中文；监管文件名称必须原文引用，不得改写

## 第二部分：数据模型与知识库改造（第一批开发）

### 改动 1：数据分级体系替换为 JR/T 0197 五级

**现状**：`DataAsset.classification` 枚举为 `公开/内部/敏感/机密`
**改造为**：

```python
class DataLevel(str, Enum):
    L5_IMPORTANT = "5级_重要数据"      # 影响国家安全/公众权益严重损害
    L4_C3 = "4级_C3鉴别信息"          # 账户密码、生物特征、鉴别凭据
    L3_C2 = "3级_C2主要信息"          # 账户信息、身份证号、KYC、住址
    L2_C1 = "2级_C1次要信息"          # 开户时间、内部办公数据
    L1_PUBLIC = "1级_公开数据"
```

- 前端下拉选项改为 5 级，**每级旁边展示典型数据举例**（JR/T 0197 附录 A 节选），辅助项目经理选择
- 提供**老 4 级到新 5 级的迁移映射**：公开→1级、内部→2级、敏感→3级、机密→4级；机密且标记 is_sensitive_pii 的生物识别类数据→4级并附加 C3 标签；迁移后保留 `legacy_classification` 字段留痕
- **知识库规则联动改造**：
  - 原 `classification: 机密` 触发的规则（SEC-V6-001 等）改为 `level >= L4_C3` 触发
  - **新增 L5 级专属规则**：触发《重要数据识别报告》生成需求、年度风险评估需求、目录备案需求
  - **C3 类专属规则**：传输/展示环节禁止明文、禁止缓存（含前端 CDN）、日志禁记

### 改动 2：安全需求新增“合规出处”字段

`SecurityRequirement` 表新增：

```python
regulatory_ref = Column(JSON)  
# 结构: [{"file": "银行保险机构数据安全管理办法", "clause": "第X条", 
#         "summary": "..."}, ...]
```

**knowledge_base.yaml 中每个模板同步增加 `regulatory_ref` 字段**，现有 38 条模板需补充对应出处，参考映射：

| 规则类别 | 主要出处 |
| --------- | --------- |
| 数据分级/加密/脱敏 | 《银行保险机构数据安全管理办法》(金规〔2024〕24号)、JR/T 0197-2020、《个人金融信息保护技术规范》JR/T 0171 |
| 敏感PII同意/出境 | 《个人信息保护法》第23/39/55条、《数据出境安全评估办法》 |
| 认证/密码/会话 | 等保2.0第三级安全要求、JR/T 0068《网上银行系统信息安全通用规范》 |
| 支付/交易 | 《商业银行信息科技风险管理指引》、JR/T 0071 |
| 组件漏洞 | 《关于加强商业银行互联网助贷业务管理的通知》中供应链相关要求、等保2.0 |
| UGC/AI/创新 | JR/T 0199-2020《金融科技创新安全通用规范》 |
| 审计日志 | 《网络安全法》第21条（留存≥6个月） |
**注意**：`regulatory_ref` 中的条款号必须使用行业通行的真实条款号，不确定的具体条文号写“参考《XX办法》”并标注“待合规部门确认”，**禁止编造具体条款号**。

### 改动 3：知识库新增“监管报送触发器”类规则

新增 trigger 类型 `regulatory_trigger`，当项目输入满足条件时，在需求清单**置顶**生成报送类需求：

| 触发条件 | 生成需求 | 依据 |
| --------- | --------- | ------ |
| 存在 L5 级数据 | 《重要数据识别与目录备案》 | 金规〔2024〕24号 |
| 数据资产 cross_border=true 或外包方为境外 | 《数据出境安全评估申报》 | 《数据出境安全评估办法》 |
| deploy_env 含外采SaaS 且 industry=finance | 《信息科技外包风险分类分级评定》 | 《银行保险机构信息科技外包风险监管办法》 |
| 项目类型 ∈ {mobile_app, mini_program} | 《移动应用程序台账登记》 | 《关于加强银行业保险业移动互联网应用程序管理的通知》 |
| 勾选 ai_feature | 《金融科技创新监管工具申报评估》 | JR/T 0199-2020 |
| final_level = 三级 | 《重要信息系统投产变更报告》提示 | 金融监管总局信息科技监管要求 |

## 第三部分：评审流程与门禁（第二批开发）

### 改动 4：新增评审节点与门禁模型

```
ReviewGate (评审门禁表)
├── gate_id / project_id
├── gate_type: initiation | requirement | design | (预留: poc / launch)
├── status: pending | in_review | passed | rejected | rectifying
├── submitted_at / reviewed_at
├── reviewer_id (安全中心评审员)
├── reviewer_opinion (评审意见, text)
├── conclusion_attachments (JSON, 附件路径)
└── version_hash (提交时全部交付物的SHA256快照)
ReviewEvidence (评审留痕表)  
├── evidence_id / gate_id / actor_id / action
├── action_type: submit | approve | reject | request_change | sign
├── timestamp / ip / comment
└── prev_hash / curr_hash  ← 链式哈希, 防篡改
```

**门禁硬校验规则**（接口层强制）：

| 门禁 | 通过条件（全部满足） |
| ----- | ----------------- |
| 立项门禁 | 定级问卷已提交且有 final_level；监管报送触发器已全部确认 |
| 需求门禁 | 生成的安全需求数 ≥ 1；每条需求 source_entity_id 非空；无 critical 级需求未确认责任人 |
| 设计门禁 | SBOM 已生成；权限矩阵 SoD 冲突 = 0 或已生成整改需求；数据字典字段 100% 关联到 L1-L5 分级 |
| （预留）POC 门禁 | 高危漏洞 = 0（本期只做数据结构，不做流程） |
不满足时接口返回 `{"gate": "design", "status": "blocked", "missing": [...]}`。

### 改动 5：角色扩展

现有 3 角色扩展为 6 角色：

```
pm (项目经理)          - 发起、填报
developer (开发中心)   - 填写技术方案
security_reviewer (安全中心评审员) - 审核、出意见
security_lead (安全中心负责人)     - 会签、终审
risk_manager (风险管理部门)        - 重大风险备案查看
auditor (内部审计)                 - 只读全量, 可导出审计视图
```

- RBAC 中间件统一拦截；审计角色只读，接口层禁止任何写操作
- **关键约束**：`pm` 不能审自己发起的门禁；`security_reviewer` 审核通过后 `security_lead` 才能终审（两步签核）

### 改动 6：文档模板调整

4 份 Word 文档内容升级：

1. 《需求规格说明书-安全需求章节》
   - 需求表格**新增“合规依据”列**（取 regulatory_ref 中的 file + clause）
   - 表格按“监管报送类 / 等保条款类 / 通用安全类”三组排序
   - 文档末尾新增“评审记录”页：评审节点、评审人、意见、签字栏、日期
2. 《总体设计说明书-安全设计章节》
   - 数据字典表分级列改为 JR/T 5 级表述
   - 新增“监管报送事项清单”章节
3. 《系统定级建议书》
   - 判定依据引用 JR/T 0071 / 公安部定级指南条款
   - 新增“安全中心复核意见”栏
4. 新增第 5 份文档：《**项目安全评审表**》——汇总各门禁状态、需求覆盖统计、漏洞概况、遗留问题，作为评审会的会议材料

## 第四部分：验收标准（随 prompt 一起发）

### 功能验收

1. 数据资产录入页可选 JR/T 5 级，页面展示典型数据举例
2. 老种子数据执行迁移脚本后：原“机密”资产落到 4 级、生物识别附加 C3 标签，`legacy_classification` 保留原值
3. 任取一条生成需求，`regulatory_ref` 非空且引用的文件名真实存在
4. 种子项目“个人网银系统”触发**监管报送类需求 ≥ 4 条**（L4 资产不触发 L5 报送、无境外供应商不触发外包评定——需准确）
5. 需求门禁接口在“某 critical 需求未指定责任人”时返回 blocked 且 missing 列表准确
6. pm 用户调用审核接口返回 403；auditor 调用任何 POST 返回 403
7. ReviewEvidence 连续提交 3 条动作后，curr_hash 与链上前序记录一致（可写单测验证）

### 测试验收

1. pytest 新增用例：
   - 5 级分级联动规则触发断言（L5 触发报送、L4 触发 C3 规则）
   - regulatory_ref 完整性断言（遍历所有模板非空）
   - 门禁阻断逻辑正反向用例
   - 哈希链完整性用例
2. 原有 38 条规则的存量测试全部保持绿色（规则 ID 不变，仅内部实现调整）

### 明确不做（本期范围外）

- 厂商门户、外部系统对接（OA/4A/SIEM）

- LLM 润色
